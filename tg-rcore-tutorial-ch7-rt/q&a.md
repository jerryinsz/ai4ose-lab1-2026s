# 核心问题与解答 (Q&A)

**Q1：为什么不直接使用 `tg_sync` 里的 Mutex，而是要自己改写内核的 `mutex_lock` 逻辑？**
**A1**：`tg_sync` 提供的通常是基于原子操作的 SpinLock 或者简单的阻塞锁。而要实现 PI（优先级继承），锁机制必须与调度器深度耦合。它需要知道“当前是谁持有我”、“谁在等我”，并且有权限去修改持有者的 `TCB.dynamic_priority`，这只能在内核的 `SyscallContext` 层拦截并注入逻辑。

**Q2：如果 L 持有锁，M 抢占 L，H 等待 L。此时来了个更高优先级的任务 X，也需要这个锁，PI 应该怎么处理？**
**A2**：这被称为**传递性优先级继承**。在完备的 PI 协议中，L 的优先级应该提升到所有等待该锁的任务中的最高优先级。即如果 X 的优先级高于 H，L 的动态优先级应该再次被提升至 X 的级别。本实验为了简化模型，目前仅支持了单层级的提升，但在真正的 RTOS 中必须考虑传递性。

**Q3：在 `processor.rs` 中，为什么 EDF 的 `fetch` 采用遍历而不是维护一个有序队列？**
**A3**：维护有序队列（如优先队列/二叉堆）在插入时需要 $O(\log N)$ 的时间复杂度。但在实验环境中，就绪队列长度通常较小（<10），直接遍历寻找 `min(deadline)` 也是非常快的，而且实现上更为简单。如果系统任务极多，改用 `BTreeSet` 或 `BinaryHeap` 是更好的工程选择。
